00先说结论：能做成，但只能做到「半自动」

我把 DeepSeek 平台的授权协议实测了一遍（不是查文档，是真发请求），结果如下。

好消息：DeepSeek 平台有一个可用的 OAuth 授权通道，端点 POST platform.deepseek.com/auth-api/v0/dsh/auth_init 实测返回 code=0 和一个真实的 authorize_url（形如 /dsh/authorize?authorize_id=…，有效期 600 秒）。这意味着「点按钮 → 打开授权页 → 拿回凭据」这条路真实存在。
坏消息：这个通道是 DeepSeek 自家桌面客户端（DSH）专用的，没有对第三方开放注册。 它的 redirect_uri 只接受 loopback 地址——我实测了三种： http://127.0.0.1:8888/oauth/callback 通过； dsbar://oauth/callback 被拒（PAYLOAD_SCHEMA_MISMATCH）； https://evil.example.com/cb 也被拒。 所以不能用 Android 的 App Links / 自定义 scheme 直接跳回，必须在手机里起一个本地 HTTP 服务接回调。

02流程

四段，用户只看见「点按钮」和「回到 App 已配好」。

Step 1 · App
点「浏览器登录」
本地起一个只监听 127.0.0.1 的临时 HTTP 服务，随机端口。
Step 2 · App
请求 auth_init
生成 PKCE verifier/challenge/state，拿到 authorize_url。
Step 3 · 浏览器
打开授权页
未登录则先登录；已登录直接显示「授权 DS Bar」。
Step 4 · 回跳
浏览器跳回本地服务
App 校验 state → 换取凭据 → 存好 → 显示成功页。
关键约束：浏览器要能访问到手机里的 127.0.0.1。 同一台手机上这是成立的——浏览器和 App 共享同一个 loopback。

05安全

风险应对
回调被劫持标准 PKCE（S256）+ 随机 state，回调里 state 不符直接丢弃
其它 App 抢占本地端口只绑 127.0.0.1，不绑 0.0.0.0；端口随机；收到一次回调立即关闭 server
凭据外泄token 只进应用私有 SharedPreferences，不写日志、不进 Dart 层缓存（沿用现状）
授权链接被分享链接绑定单次 authorize_id 与 PKCE verifier，别人打开也换不到你的 token
明文网络全程 HTTPS 到 platform.deepseek.com；loopback 不经过网络

06取舍与不做的部分

做

  • 一键浏览器登录，成功即配好 userToken
  • 失败/过期有明确退路，回到手动粘贴
  • 旧的手动填入口保留，不删
  • 登录态显示账号打码邮箱（若能拿到）

不做

  • 不内嵌 WebView 做登录 —— DeepSeek 登录页有风控，WebView 里大概率过不去，且更容易被判定为异常
  • 不自动读取浏览器 Cookie —— 那需要抓别的 App 的数据，Android 上不可行也不该做
  • 不申请任何新权限
  • 不引第三方依赖（延续现在的零依赖）
必须说清楚的风险：这套授权接口是 DSH 桌面客户端专用的非公开接口，DeepSeek 没有承诺对第三方开放。 它随时可能收紧或变更，届时一键登录会失效。 所以实现上会把它做成「锦上添花」而非唯一路径——手动粘贴那条路必须始终可用。 这也是为什么态 4 一定要有「改用手动填」这个出口。

08需要你定的三件事

问题我的建议
