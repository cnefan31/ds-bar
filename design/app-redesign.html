DS Bar · 主界面重设计

Linear 式深色数据看板 · 余额为王 · 单页纵向流。按 372×820 逻辑像素绘制，与真机 1080×2340 同比例。 本页只出稿，不改代码；你确认后我再动 Flutter。
先说清这版解决什么问题：
  1. 现在首屏是「卡片套卡片」：余额一张卡、今日一张卡、本月一张卡、按 key 一张卡、按模型一张卡、key 状态又一张卡。六张同等权重的卡，眼睛没有落点，也不知道先看什么。
  2. 改法：把六张卡压成三个视觉层级 —— ① 无边框的主视觉区（余额 + 三个关键数，直接铺在画布上）② 一组指标格与图表（细描边）③ 可滚动列表（细描边）。层级靠留白与字号，不靠六层卡片边框。
  3. 同一屏容纳的信息量更多：首屏从「余额 + 今日」两行，变成「余额 + 三项拆分 + 今日四指标 + 7 日趋势」。这些数据现在都有，只是被卡片切碎了。

三 · 设计语言（从哪抄的、为什么）

取法对象与具体规则

  • Linear：近黑画布 #010102 而非纯黑；表面逐级提亮 #0F1011 → #18191A；1px hairline 分隔；单一强调色 #5E6AD2，只用于品牌点与主按钮，不做装饰。
  • Stripe / Vercel Dashboard：数字用等宽字体 + tabular-nums，位数不跳动；标签淡化、数值加重，靠字重而非颜色分层。
  • Apple Health / 记账类 App：主指标独占一行，字号跨级（52 → 14 → 10.5sp），一级视觉只有一个。
  • Material 3：底部两 tab 导航、下拉刷新、列表行最小 44dp 触控区。

刻意不做的

  • 不加六张卡片：卡片越多层级越平，边框成了噪声。改用一个主视觉区 + 少量细描边容器。
  • 不用彩色渐变与玻璃拟态：数据看板要冷静准确，渐变会让人怀疑数字是否被装饰过。
  • 不放大饼图：2–3 个模型的占比，一条横向占比条比饼图读得快。
  • 不给每个数配图标：图标占位多、区分度低，纯数字更快扫读。
  • 不用红色标消费：红色留给真正的错误。支出用负号 −¥0.71 与中性色。

四 · 每个数字的真实来源

设计稿里出现的每一项，都必须在接口里有对应字段。拿不到的一律不画。
界面元素数据来源说明
余额大字 / 充值 / 赠送官方 /user/balance 三个字段直接对应：total_balance、topped_up_balance、granted_balance。
可用状态点官方 is_available 布尔值，直接映射绿/红点。
今日消费 / token / 请求平台 usage/export 按本地时区 0 点起的窗口统计。
今日命中率平台 usage/amount 命中 /（命中 + 未命中）自行计算，接口不直接给。
「较昨日 +12%」派生 由 days 数组末两天相除得到，需要至少 2 天数据；不足时这一处不显示。
本月趋势图平台 usage/amount 的 days 逐日 token，直接映射柱高。
峰值 / 均值派生 由 days 自行求最大与平均。
按 Key 金额与 token平台 usage/export CSV 按 api_key_name 聚合；本地名称与平台名称不一致时会分成两行。
按 Key 占比条派生 单 key 消费 / 各 key 合计。
按 Model 占比条平台 usage/cost 分模型费用，横向占比条。
凭据状态点逐 key 调余额接口 200 即有效，401/403 即失效。
赠送额到期时间无 接口不给。初稿曾写「12 天后到期」，已删除。要显示只能在本地记录首次看见赠送额的时间来估，属推算，不做。
单 Key 余额无 余额是账户级，同账号所有 key 共享一个余额，不存在「每 key 各自余额」。设计上不出现分 key 余额。
